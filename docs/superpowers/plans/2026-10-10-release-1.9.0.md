### Task 15：流式「即发即入框 + 可静音」全路径统一（真机验收 P1 抖出的主缺陷）

用户定的语义（**注意：不是“中止合成”**）：点停止 = **只静掉扩声器与虚拟麦克风的播放**，
**合成继续跑完、消息照常入列表、音频文件照常产出**，只是不再响。

1. Rust：`StreamPlayer` 新增“静播”控制（Mute）——只停 sink，**不 Abort 会话、不停拉块**，
   文件继续写完整；与现有 Abort 语义区分开（遥控/抢占旧流仍用 Abort）。
2. Rust：消息 id 与 `audio/{fid}.wav` 路径的分配**提前到 `stream_start` 之前**，抽出纯函数
   （`plan_stream_paths` 类）便于单测；会话建立成功后 emit `tts:streaming`
   `{id, content, audio_path, engine, created_at}`。
3. 前端：订阅 `tts:streaming` → 立即插入**占位气泡**（清空输入框、置底）；占位气泡带
   「⏹ 静播」按钮调 `tts_stream_mute`，**重播/收藏暂禁用**（wav 未写完，对应 Task 9-M-3 的已知隐患）；
   命令返回后用同 id 原地换成正式消息；失败则占位气泡转错误态（不静吞）。
4. 消除双播：把宿主在播的 `audio_path` 经现有 `va:play:start`/`playback:started` 同步到前端 `playingPath`；
   `playAudio` 起 `<audio>` 前先静掉宿主（否则同一消息两路声音重叠）。
5. 全路径统一：主窗发送、语音输入直接发送、浮窗 QuickInput、手机遥控发字——事件由后端发，
   各窗口只是订阅者（用户已选定全路径）。
6. 非流式引擎（MOSS/Edge/Genie/Hojo）行为不变：不发 `tts:streaming`，走原有“完成后自动播”。
7. 测试：Rust 路径预分配/事件载荷纯函数单测 + “静播不终止合成”状态单测；前端占位气泡
   状态机（streaming→done/muted/error）抽纯函数 + vitest。门禁全量复跑 + 真机复验
   （出声前气泡已在、点静播后不再响但消息仍落库、点气泡不双播）。
