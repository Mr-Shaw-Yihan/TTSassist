# 消息发送与播放体验（非阻塞发送 · 气泡状态机 · 播放态同步）设计

> 状态：**设计已用户批准**（2026-10-13，主线会话）。承接悬浮球移除后的 1.9.0 范围扩项；
> 实现走 writing-plans 出的独立实施计划，逐项 TDD + 全量门禁 + 真机验收。
> 目标并入 **1.9.0**（用户 2026-10-13 拍板：四项全做完、验过，再进 P3 合 main / 发布）。

## 一、背景与四诉求

用户在真机验收期间反馈，现发送流体验有 4 处问题（用户复述并确认理解一致）：

1. **非阻塞发送**：像 QQ 一样，发送即把文本变成消息气泡入列，关于这条消息的状态都在气泡上显示，**解放输入框**（现状：`handleSend` `await generateTTS` 要等整条合成完成才返回，这期间输入框处于"发送中"被占用）。
2. **发送即定位最新**：点发送后列表自动滚到最新那条气泡（现状：仅"原本已在底部"才滚、且发生在合成完成时，占位气泡插入那一刻不滚，够不到播放/停止）。
3. **首启麦克风 bug**：前几次合成/播放音频没进虚拟麦克风，直到在"设置-虚拟麦克风"点测试触发一次后，后续才正常。
4. **播放态同步**：发送触发的自动播放要与气泡的播放状态同步，且能被气泡的播放按钮控制（现状：宿主已把该条播进虚拟麦克风+扬声器，但那条气泡的播放按钮显示"未播放"，点它不停宿主、反而又起一遍新播放 = 双播）。

## 二、关键现状（代码事实，非推测）

- 后端流式管线 `commands/tts_stream.rs`：`generate_tts_stream` **跑完整条流才返回** `StreamTtsResult{message, host_played}`；会话建立、即将出声那刻**已 early 发 `tts:streaming` 事件**（载荷 `StreamingNotice{id, content, audio_path, engine, created_at}`）。
- 宿主**同一时刻只跑一条流**（`active_stream_slot: Mutex<Option<ActiveStream>>`）；已有中止命令 `tts_stream_stop`。
- 前端 `App.tsx`：
  - `handleSend`(521) `await generateTTS(text)` → `settleStreaming` → `if (atBottom) scrollToBottom()` → `if(hostPlayed) return;` 否则延迟 `playAudio`。
  - `tts:streaming` 监听(205) 已入占位气泡（`withStreamingPlaceholder` + `streamingIds`）。
  - `playingPath`/`playingPathRef`(78/107)、`bail`(≈394) 播放态；`scrollToBottom`(301) 已存在。
- 发往虚拟麦克风的两条路径都 gate 在 `mic_send_enabled && !mic_output_device.is_empty()`：
  - 阻塞路径 `tts.rs:124-126` → `mic.play(abs, mic_device, mic_volume)`（走 `MicPlayback` 专用线程，`setup_stream_for_device` 懒开 `OutputStream`）。
  - 流式路径 `tts_stream.rs:238-240 / 563` → 播放线程内**各自** `find_device_by_name` + `OutputStream::try_from_device`。
- 失败语义（现状）：流中途失败**不落消息记录**；前端 `handleSend` catch 里**摘掉占位 + 抛给 InputBox 走 showInfo**（列表不留失败痕迹）。

## 三、设计（六块）

### A. 非阻塞发送
- `handleSend` 改为：点发送后**立即**清空/释放输入框（可继续打字），插入一条 `合成中` 占位气泡，并把 `generateTTS` 的等待转为**后台任务**（不挡 UI、不挡输入框）。
- 前端以事件驱动气泡终态：`tts:streaming`（已开始，带 audio_path）→ 合成中/正在播放；成功落库（`message:changed` 或后台任务返回的 message）→ 完成；失败 → `tts:failed`（新增）。
- 后端**新增事件 `tts:failed(id, reason)`**：流中途失败时，对已 early 发过 `tts:streaming` 的那个 id 补发失败通知（携带简短中文原因），供气泡转失败态。非流式（MOSS/Edge/Genie 等阻塞引擎）无 early 事件：由后台任务的 resolve/reject 直接驱动完成/失败。

### B. 气泡状态机
- 每条气泡状态：`合成中 → 完成(可播) | 失败(显示原因 + 「重试」)`。
- 流式"合成中"即"先出声后结束"的播放中态。
- **失败保留气泡 + 重试**（用户定）：重试 = 用同一文本重新走发送；旧失败气泡被替换/收敛。放弃"宁缺毋残"（失败不再默默删气泡）。
- 状态集合最小化：不做进度百分比、不做部分播放（YAGNI）。

### C. 发送键置灰 + 二次点打断（用户选：连点两次）
- 有任一条在合成时：发送按钮**置灰但仍可点**。
- 第 1 下：不发送，轻提示"上一条还在合成，再点一次将打断并改发这条"（前端本地提示，不弹模态）。
- 第 2 下（连点）：`tts_stream_stop` 打断当前合成/播放 → 摘旧占位气泡 → 立即发送并合成这条新文本。
- 单条完成/失败后，发送键解禁。

### D. 发送即定位最新
- 点发送即把列表滚到底（滚到那条新占位气泡），不再只在"原本在底部"或"完成时"才滚。用户主动向上翻阅时不打断（沿用现有 `atBottom`/定位按钮），但"发送"这个动作本身视为"我要看最新的"。

### E. 播放态同步与互斥（bug④）
- 宿主开始流式播放某条时 `emit va:play:start(audio_path)` → 前端把该条设为 `playingPath`，气泡按钮显示"播放中/⏹"。
- 点该条播放按钮：
  - 若该条正是宿主在播的 → 点它=停宿主（静播：只静音、合成继续/已落库，沿用 Task 15 静播语义与 `tts_stream_stop`/静播命令）。
  - 否则 → 走 `playAudio` 正常整段播放。
- `playAudio` 起 `<audio>` 前先静宿主（`emit va:play:stop`/停活动流），杜绝同一音频双播。
- 复用既有 `va:play:start`/`playback:started` 通道，**补齐流式路径**未接通的那半（Task 15 item 4 遗留）。

### F. 首启麦克风 bug③（✅ 已定位 + 已修：启动热启）
> 定案（2026-10-13，取证日志 + 用户真机复现）：根因 = **Windows 音频端点冷启动首开偶发不出声**
> （open 常返回成功、但头几帧没真路由），之前靠用户手动点“设置-虚拟麦克风测试”把端点热起来才行。
- **修法**：应用启动即**自动热启**——检出 VB-CABLE 输出设备、播一小段内置原音（与手动测试同一 `MicPlayback` 路径）激活端点，用户无感。
- **只作用于热启**：热启只认检出的 cable（`find_virtual_cable_output_device`），**不依赖 `mic_output_device`**；发送/其它设备选择仍由用户定，互不干涉。
- 门控：`mic_send_enabled` 且检到 cable 才热；播完 `MicPlayback` 线程持有该设备 OutputStream（复用）。
- 手动“测试”的 440Hz 正弦换成内置 `mic_warm.wav`（打包进二进制）；提速系数 `MIC_WARM_SPEED` 现为 **1.0（原音）**——rodio `.speed()` 提速必升调，不变调加速需时间伸缩、不值得，故用原音。
- 真机验收：冷启动、不手动点测试，第一条消息对方即能听见（已过）。

## 四、影响面
- 前端：`src/App.tsx`（发送/滚动/播放同步）、`src/components/Chat/InputBox.tsx`（置灰+二次点打断语义、composer 不阻塞）、消息气泡组件（状态机 + 重试 + 播放控制）。
- 后端：`src-tauri/src/commands/tts_stream.rs`（发 `tts:failed`、va:play:start 流式补齐、mic 打开取证/修法）、`src-tauri/src/commands/tts.rs`（阻塞路径失败也发 `tts:failed`）、可能 `mic.rs`。
- 事件契约：`tts:streaming`(已有) / `tts:failed`(新增) / `va:play:start`(已有，补齐流式) / `tts_stream_stop`(已有)。

## 五、测试策略
- 前端 vitest：气泡状态机纯函数（合成中→完成/失败→重试、二次点打断的迁移）；发送后不阻塞、置灰语义。
- 后端单测：`tts:failed` 载荷与发射时机（流式与阻塞两路径）；mic 打开重试（F 定案后补）。
- 真机：①连续打字发送不卡输入框、状态在气泡；②发送即滚到最新；③宿主播放时气泡显示播放中、点击能停不双播；④失败气泡保留可重试；⑤首启麦克风按 F 取证与复验。

## 六、不做（YAGNI）
- 不做多流并发合成（保持"一次一条流"，靠打断而非并行队列）。
- 不做合成进度百分比、不做失败气泡的编辑后重发（重试=同文本原样重发）。
- 不改遥控/浮窗等非主窗发送入口的事件语义（它们靠 `message:changed`/`tts:streaming` 收敛）。
